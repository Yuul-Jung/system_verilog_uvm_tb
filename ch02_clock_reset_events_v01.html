제02장 · Clock·Reset·이벤트

기존 PWM RTL로 클록·리셋·설정 반영의 실제 시간 관계를 읽는 2시간 실습

6부 · 24장각 장 2시간 · 1시간씩 분리기존 RTL 재사용

00학습 흐름 · 시간에 따라 변하는 회로

제01장에서는 클록이 없는 UART Echo 연결 회로를 시험했습니다. 제02장에서는 클록에 따라 내부 상태가 달라지는 PWM(펄스폭 변조) 회로를 검증합니다. 이미 구현된 pwm_core를 그대로 사용하여 클록 생성 → 리셋 → 설정 요청 → 주기 경계 반영 → 출력 관찰을 따라갑니다.

구간시간실습 내용
1교시0~60분클록 문법, 상승·하강 에지, 원본 PWM의 Shadow 구조, 시간표 분석
2교시60~120분전체 테스트벤치 작성, Ubuntu 실행, 파형 및 리셋 시점 해석

실습 대상은 기존 part02_1/ch04/rtl/pwm_core.v입니다. 보드가 없어도 시뮬레이터만 있으면 검증할 수 있으며, 원본 RTL·기존 성공 프로젝트는 수정하지 않습니다.

011교시 ① · always, #, posedge, negedge (0~20분)

Clock(클록, 회로의 동작 박자)은 일정한 주기로 0과 1을 반복합니다. always #5 clk = ~clk;는 5ns마다 클록을 반전하므로 한 주기는 10ns, 주파수는 100MHz(메가헤르츠)입니다. 여기서 #5는 `timescale 1ns/1ps를 기준으로 계산합니다.

클록·이벤트 핵심 문법 · Verilog · 교육용 발췌
initial clk = 1'b0;      // 시뮬레이션 시작 시 LOW
always #5 clk = ~clk;    // 5ns마다 반전: 10ns 주기

@(posedge clk);          // 다음 상승 에지까지 대기
@(negedge clk);          // 다음 하강 에지까지 대기
#1;                      // 1ns 지난 뒤 출력 관찰

initial은 시작할 때 한 번 실행하고, always는 반복 수행합니다. posedge는 0에서 1로 상승하는 순간, negedge는 1에서 0으로 하강하는 순간을 가리킵니다.

왜 TB는 하강 에지에서 입력을 바꿀까요? 원본 PWM은 상승 에지에서 입력을 읽습니다. 같은 상승 에지에서 TB도 입력을 바꾸면 실행 순서를 확신하기 어려운 Race Condition(레이스 컨디션, 실행 순서 경쟁)이 생길 수 있습니다. 하강 에지에 미리 값을 바꾸면 다음 상승 에지에서 안정된 입력을 읽습니다.

반대로 DUT가 내부 레지스터를 갱신하는 상승 에지 직후에는 비차단 대입 <= 결과가 아직 반영되기 전일 수 있습니다. 이번 장에서는 관찰용으로 #1을 둡니다. 이 지연은 하드웨어에 합성되는 회로 지연이 아닙니다.

021교시 ② · 원본 PWM의 포트와 상태 (20~40분)

기존 pwm_core는 새로운 설정을 받은 즉시 파형에 반영하지 않습니다. 먼저 Shadow(섀도, 대기 설정 레지스터)에 값을 저장하고, 현재 PWM 주기가 끝나는 경계에서 Active(액티브, 실제 사용 설정)로 옮깁니다. 따라서 cfg_apply를 1로 만들었다고 출력이 바로 변하지는 않습니다.

실제 포트의미
clk / resetn상승 에지 클록 / LOW 활성 리셋
cfg_apply새 설정을 Shadow에 보관하도록 요청
cfg_period / cfg_duty주기·HIGH 구간을 나타내는 클록 개수
cfg_enable / cfg_polarity출력 허용 / 극성 설정
pendingShadow 값을 Active에 적용하기 전 대기 표시
active_period / active_duty현재 적용 중인 주기·듀티
active_enable / active_polarity현재 적용 중인 활성화·극성
pwm_out최종 PWM 출력

RESET_PERIOD를 교육용으로 8클록으로 줄이고, cfg_period=8, cfg_duty=3으로 요청합니다. 활성화 이후 주기는 80ns, HIGH 구간은 30ns로 듀티비가 37.5%입니다.

리셋은 두 층으로 나뉩니다. always @(posedge clk) 내부의 레지스터는 상승 에지에서 resetn을 확인하므로 동기식으로 초기화됩니다. 반면 pwm_out은 조합식에서 resetn을 직접 사용하므로 LOW 리셋을 인가하면 상승 에지 이전에도 곧바로 출력이 0으로 차단됩니다.

031교시 ③ · 시간축을 실제 코드와 맞추기 (40~60분)

클록은 5, 15, 25, 35…ns에 상승합니다. 입력은 20, 30, 40…ns의 하강 에지에 바뀌며, 로그는 DUT 레지스터가 갱신된 다음 1ns에 기록합니다.

시각동작예상 상태
20nsresetn 해제25ns 상승 에지부터 카운터 진행
30nscfg_apply HIGH새 설정 요청
35nsShadow 저장pending=1, Active 듀티는 0 유지
95nsPWM 주기 경계pending=0, Active 듀티 3, 출력 HIGH
125ns듀티 구간 종료출력 LOW
175ns다음 PWM 주기출력 HIGH
190nsLOW 리셋 재인가조합식의 출력 즉시 LOW
195ns리셋 상태의 상승 에지내부 Active 값 초기화

35ns에 이미 요청을 저장했는데도 95ns까지 출력이 바뀌지 않는 이유는, counter가 active_period-1의 경계에 도달해야만 Shadow 값이 Active 값으로 옮겨가기 때문입니다.

042교시 ① · 전체 테스트벤치 작성 (60~85분)

테스트벤치는 세 가지 흐름을 병렬로 수행합니다. 클록 생성 always, 출력 관찰 always @(posedge clk), 리셋과 설정 입력을 넣는 initial입니다. PWM 원본 포트명은 바꾸지 않습니다.

tb/ch02/tb_pwm_clock_reset.sv · SystemVerilog · 신규 TB · RTL 시뮬레이션 미실행
`timescale 1ns/1ps
// 제02장: 기존 pwm_core의 클록·리셋·주기 경계를 관찰한다.
// DUT 원본은 변경하지 않는다. 자동 PASS/FAIL 판정은 제04장에서 다룬다.
module tb_pwm_clock_reset;
    reg         clk;
    reg         resetn;
    reg         cfg_apply;
    reg  [31:0] cfg_period;
    reg  [31:0] cfg_duty;
    reg         cfg_enable;
    reg         cfg_polarity;

    wire        pwm_out;
    wire        pending;
    wire [31:0] active_period;
    wire [31:0] active_duty;
    wire        active_enable;
    wire        active_polarity;

    // (추가) 실제 DUT의 모든 포트를 원래 이름으로 연결한다.
    // RESET_PERIOD만 교육용으로 8클록으로 축소한다.
    pwm_core #(.RESET_PERIOD(32'd8)) dut (
        .clk             (clk),
        .resetn          (resetn),
        .cfg_apply       (cfg_apply),
        .cfg_period      (cfg_period),
        .cfg_duty        (cfg_duty),
        .cfg_enable      (cfg_enable),
        .cfg_polarity    (cfg_polarity),
        .pwm_out         (pwm_out),
        .pending         (pending),
        .active_period   (active_period),
        .active_duty     (active_duty),
        .active_enable   (active_enable),
        .active_polarity (active_polarity)
    );

    // 5ns마다 반전하므로 클록의 전체 주기는 10ns이다.
    initial clk = 1'b0;
    always #5 clk = ~clk;

    // 출력과 내부 신호를 VCD 파일에 기록한다.
    initial begin
        $dumpfile("ch02_pwm_clock_reset.vcd");
        $dumpvars(0, tb_pwm_clock_reset);
    end

    // 상승 에지 이후 1ns를 기다려 비차단 대입 결과를 읽는다.
    // #1은 하드웨어 지연이 아니라 테스트벤치 관찰용 시간 이동이다.
    always @(posedge clk) begin
        #1;
        $display("POS t=%0t ns rst=%b apply=%b pending=%b period=%0d duty=%0d en=%b pwm=%b",
            $time, resetn, cfg_apply, pending,
            active_period, active_duty, active_enable, pwm_out);
    end

    initial begin
        // 0~20ns: 활성 LOW 리셋을 유지한다.
        resetn       = 1'b0;
        cfg_apply    = 1'b0;
        cfg_period   = 32'd8;
        cfg_duty     = 32'd3;
        cfg_enable   = 1'b1;
        cfg_polarity = 1'b0;
        $display("=== CH02 PWM CLOCK / RESET START ===");

        // t=20ns 하강 에지에 리셋 해제.
        @(negedge clk);
        @(negedge clk);
        resetn = 1'b1;

        // t=30~40ns 설정 요청, t=35ns Shadow 저장.
        @(negedge clk);
        cfg_apply = 1'b1;
        @(negedge clk);
        cfg_apply = 1'b0;

        // t=190ns: PWM이 HIGH인 구간에서 리셋 재인가.
        repeat (15) @(negedge clk);
        resetn = 1'b0;
        #1;
        // 리셋 입력만 LOW로 바뀌어도 조합 출력은 즉시 LOW가 된다.
        $display("EVENT t=%0t ns resetn=%b active_duty=%0d pwm=%b",
            $time, resetn, active_duty, pwm_out);

        // t=195ns 순차 레지스터 리셋, t=200ns 리셋 해제.
        @(negedge clk);
        resetn = 1'b1;

        repeat (4) @(negedge clk);
        $display("=== CH02 END: OBSERVATION ONLY ===");
        $finish;
    end
endmodule

코드 풀이 — 숫자와 실제 시간의 관계

.RESET_PERIOD(32'd8)는 DUT의 초기 주기를 8클록으로 지정합니다. 10ns 클록의 8번 상승 에지 경계를 사용해 짧은 시간에 주기를 관찰할 수 있습니다.

repeat (15) @(negedge clk);는 설정 요청을 내린 40ns 이후 열다섯 번째 하강 에지인 190ns까지 기다립니다. 이 시각에 리셋을 다시 인가하면 현재 PWM이 HIGH여도 pwm_out은 LOW로 내려갑니다.

$dumpfile은 저장할 파형 파일 이름을, $dumpvars는 기록할 계층을 지정합니다. $display는 콘솔 기록, $finish는 시뮬레이션 종료입니다. 이번 장은 관찰 단계이므로 출력에 PASS를 임의로 붙이지 않습니다.

052교시 ② · Ubuntu 실행과 파형 확인 (85~100분)

제01장에서 설치한 Icarus Verilog(아이카루스 베릴로그, 오픈소스 HDL 시뮬레이터)를 그대로 사용합니다. amd_soc_rtl 아래의 과정 폴더를 기준으로 원본 PWM 파일을 읽기 전용으로 참조합니다. 다른 위치에 복제했다면 DUT_PATH 환경변수로 원본을 지정합니다.

Ubuntu 터미널 · Bash · 실행 절차 · 제작 환경에서는 미실행
# 1. 검증 과정 폴더로 이동
cd /path/to/system_verilog_uvm_tb

# 2. RTL과 테스트벤치 컴파일 및 시뮬레이션
bash scripts/run_ch02.sh

# 3. GTKWave(지티케이웨이브, 파형 분석 도구)로 결과 열기
gtkwave .build/ch02/ch02_pwm_clock_reset.vcd

# 4. 별도 저장소에 기존 PWM RTL이 있다면 파일 경로를 지정
DUT_PATH=/실제/경로/pwm_core.v bash scripts/run_ch02.sh
scripts/run_ch02.sh · Bash · 실행 스크립트 · 미실행
#!/usr/bin/env bash
# 제02장: 기존 RTL을 수정하지 않고 테스트벤치·VCD·로그를 실행한다.
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
COURSE_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"

# 과정 폴더가 amd_soc_rtl 안에 있다면 기본 DUT 경로를 사용한다.
# 독립 경로에 있다면 DUT_PATH 환경변수로 파일 위치를 지정한다.
DUT_PATH="${DUT_PATH:-$COURSE_ROOT/reference_rtl/pwm_core.v}"
TB_PATH="$COURSE_ROOT/tb/ch02/tb_pwm_clock_reset.sv"
OUT_DIR="$COURSE_ROOT/.build/ch02"

for tool in iverilog vvp; do
  if ! command -v "$tool" >/dev/null 2>&1; then
    echo "ERROR: $tool 명령이 없습니다. sudo apt install iverilog"
    exit 2
  fi
done
if [[ ! -f "$DUT_PATH" ]]; then
  echo "ERROR: DUT 파일 없음: $DUT_PATH"
  echo "사용법: DUT_PATH=/실제/경로/pwm_core.v bash scripts/run_ch02.sh"
  exit 2
fi

mkdir -p "$OUT_DIR"

# SystemVerilog 문법과 원본 PWM 회로를 함께 컴파일한다.
iverilog -g2012 -s tb_pwm_clock_reset \
  -o "$OUT_DIR/simulation.vvp" "$DUT_PATH" "$TB_PATH"

# 실행 로그와 파형을 작업 폴더에 저장한다.
(cd "$OUT_DIR" && vvp simulation.vvp | tee output.log)
echo "로그: $OUT_DIR/output.log"
echo "파형: $OUT_DIR/ch02_pwm_clock_reset.vcd"

iverilog는 두 파일을 컴파일하고, vvp는 시뮬레이션을 실행합니다. 성공적으로 실행되면 .build/ch02/output.log와 .build/ch02/ch02_pwm_clock_reset.vcd가 생성됩니다.

파형에서 clk, resetn, cfg_apply, pending, active_duty, pwm_out을 함께 표시하면 경계와 동기식 리셋의 차이를 직접 볼 수 있습니다.

062교시 ③ · 예상 결과 해석 (100~110분)

다음은 원본 pwm_core.v의 순차·조합 논리와 TB 입력 시간표를 대조해 계산한 예상 로그 일부입니다. 전체 출력이 아니라 주요 행만 표시했고, 실제 실행 로그는 아닙니다.

output.log 중요 시점 · TEXT · 예상 출력 · 실제 실행하지 않음
POS t=26 ns rst=1 apply=0 pending=0 period=8 duty=0 en=0 pwm=0
POS t=36 ns rst=1 apply=1 pending=1 period=8 duty=0 en=0 pwm=0
POS t=96 ns rst=1 apply=0 pending=0 period=8 duty=3 en=1 pwm=1
POS t=126 ns rst=1 apply=0 pending=0 period=8 duty=3 en=1 pwm=0
POS t=176 ns rst=1 apply=0 pending=0 period=8 duty=3 en=1 pwm=1
EVENT t=191 ns resetn=0 active_duty=3 pwm=0
POS t=196 ns rst=0 apply=0 pending=0 period=8 duty=0 en=0 pwm=0

t=36ns: cfg_apply가 35ns 상승 에지에 읽혀 Shadow 값이 보관됩니다. pending=1이지만 Active 듀티는 아직 0이므로 PWM은 LOW입니다.

t=96ns: 95ns 상승 에지에 주기 경계가 발생해 Active 듀티가 3으로 바뀌고 PWM이 HIGH가 됩니다. 이후 125ns 상승 에지에서 카운터가 3이 되어 LOW로 내려갑니다. 다음 175ns 상승 에지에 다시 HIGH가 됩니다.

t=191ns: 리셋을 내린 즉시 조합 출력은 LOW지만, active_duty는 여전히 3입니다. t=196ns: 195ns 상승 에지에 내부 레지스터가 초기화되어 Active 듀티도 0이 됩니다.

결과가 다르면 입력을 negedge에서 변경했는지, RESET_PERIOD가 8인지, 설정 적용 시점에 pending이 1이었는지 순서대로 확인합니다.

08참고 · 원본 pwm_core 전체 코드

아래는 재사용한 기존 RTL 원본 전문입니다. 표·도식·테스트벤치의 신호명과 원본 포트·상태명을 직접 대조할 수 있습니다. 기존 소스는 변경하지 않았습니다.

part02_1/ch04/rtl/pwm_core.v · Verilog · 원본 · Blob SHA e813f3fb107bd327054d11e0b397817b8e7bd813
`timescale 1ns/1ps
// P2-04: 보드와 무관한 단일 채널 범용 PWM 코어.
// (추가) period와 duty는 클록 횟수 단위. 0%/100%는 지속 LOW/HIGH.
// (추가) 설정은 주기 마지막 경계에서만 활성값으로 반영.
module pwm_core #(
    parameter [31:0] RESET_PERIOD = 32'd100000
)(
    input  wire        clk,
    input  wire        resetn,
    input  wire        cfg_apply,
    input  wire [31:0] cfg_period,
    input  wire [31:0] cfg_duty,
    input  wire        cfg_enable,
    input  wire        cfg_polarity,
    output wire        pwm_out,
    output reg         pending,
    output reg [31:0] active_period,
    output reg [31:0] active_duty,
    output reg         active_enable,
    output reg         active_polarity
);
    reg [31:0] counter;
    reg [31:0] shadow_period;
    reg [31:0] shadow_duty;
    reg        shadow_enable;
    reg        shadow_polarity;

    wire boundary = (counter >= active_period - 32'd1);
    wire duty_high = (counter < active_duty);

    // (주의) enable=0이면 polarity와 관계없이 LOW로 차단.
    // (설명) 기본 polarity에서 active_duty=0이면 항상 LOW,
    //         active_duty=active_period이면 항상 HIGH.
    assign pwm_out = resetn && active_enable &&
                     (active_polarity ? !duty_high : duty_high);

    always @(posedge clk) begin
        if (!resetn) begin
            counter         <= 32'd0;
            active_period   <= RESET_PERIOD;
            active_duty     <= 32'd0;
            active_enable   <= 1'b0;
            active_polarity <= 1'b0;
            shadow_period   <= RESET_PERIOD;
            shadow_duty     <= 32'd0;
            shadow_enable   <= 1'b0;
            shadow_polarity <= 1'b0;
            pending         <= 1'b0;
        end else begin
            if (boundary) begin
                counter <= 32'd0;
                if (pending) begin
                    active_period   <= shadow_period;
                    active_duty     <= shadow_duty;
                    active_enable   <= shadow_enable;
                    active_polarity <= shadow_polarity;
                    pending         <= 1'b0;
                end
            end else begin
                counter <= counter + 32'd1;
            end
            // (추가) 경계와 APPLY가 겹치면 새 값은 다음 경계에 적용.
            // 여러 APPLY가 겹치면 최종 요청값을 우선하는 단일 Shadow 구조.
            if (cfg_apply) begin
                shadow_period   <= cfg_period;
                shadow_duty     <= cfg_duty;
                shadow_enable   <= cfg_enable;
                shadow_polarity <= cfg_polarity;
                pending         <= 1'b1;
            end
        end
    end
endmodule

출력은 resetn과 active_enable, counter < active_duty의 결과에 의해 결정됩니다. pending과 boundary의 코드 조건을 함께 읽으면 앞선 시간표와 일치합니다.
